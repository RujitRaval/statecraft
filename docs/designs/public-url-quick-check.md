## Problem Statement

Statecraft currently asks a developer to install the package, initialize configuration, define routes and states, and then run a scan before they see value. That setup is appropriate for deterministic product-state coverage, but it is too much friction for someone who only wants to point Statecraft at an existing website and understand what the tool can find.

Add a zero-config command:

```bash
npx statecraft check https://example.com
```

The command should safely inspect a small public surface, find high-confidence browser and responsive defects, generate the normal local report, and offer an explicit overwrite-safe path to save the discovered pages as a permanent Statecraft configuration.

## What Makes This Cool

The first-run moment is not “Statecraft took screenshots.” It is:

> “I gave it one URL, waited about a minute, and it found a real mobile or browser error I did not know existed.”

One command should produce side-by-side evidence across important pages, mobile and desktop viewports, and light and dark browser preferences. The report should identify the exact URL, viewport, diagnostic, assertion, and screenshot behind each result. A successful run should then turn discovery into adoption by offering a permanent, reviewable config without asking the user to re-enter the routes Statecraft already found.

## Constraints

- Keep Statecraft local-first. Do not upload URLs, screenshots, reports, diagnostics, or discovered routes.
- Accept only absolute HTTP or HTTPS URLs. Reject URL credentials and unsupported protocols; remove the supplied URL's fragment and query before its first network request so secrets and query variants never enter discovery.
- Statecraft performs navigation only: it does not intentionally click controls, submit forms, or issue scripted mutations. Loading a page still executes that site's JavaScript and normal network requests, which may themselves change application data; users must run Quick Check only against an authorized environment where ordinary page loads are safe.
- Keep discovery on the canonical starting origin after its initial redirect. Reject or skip later cross-origin redirects.
- Crawl sequentially and attempt at most five candidate pages by default, including the start page; skipped and failed candidates consume that fixed navigation budget. Preserve deterministic breadth-first document order for the same observed rendered DOM; live-site personalization, experiments, geography, timing, and content changes can alter later observations.
- Remove fragments and queries from discovered links for the first version so tracking values, tokens, and unbounded URL variants cannot enter generated source or reports.
- Ignore `mailto:`, `tel:`, `javascript:`, download links, non-document resources, and duplicate canonical paths.
- Reuse existing diagnostic sanitization, screenshot paths, schema-v1 report validation, offline HTML generation, private file modes, symlink defenses, and coherent persistence.
- Quick Check must not claim coverage for loading, empty, error, authenticated, or other application states it cannot force.
- Generic assertions must favor precision over volume. False positives destroy the first-run experience.
- Generated project files must follow `statecraft init` safety: exclusive creation, no force flag, no symbolic-link traversal, config published last, and no deletion-based rollback.

## Premises

1. Quick Check is a discovery and onboarding mode, not a replacement for configured `statecraft scan`.
2. The one-command experience is valuable only if it produces actionable evidence, not merely screenshots.
3. A bounded five-page same-origin crawl is large enough to demonstrate value and small enough to remain predictable and polite.
4. High-confidence automatic failures for the first release are main-document navigation/HTTP failure, uncaught page error, and document-level horizontal overflow. Sanitized console messages and all subordinate request failures remain report warnings because treating optional resources, analytics, ads, extensions, or transient vendors as failures would be too noisy. Element-level clipping heuristics remain out of scope until they can be proven low-noise.
5. Mobile and desktop are fixed at `390x844` and `1440x900`. Light and dark mean browser-native color-scheme preferences; Quick Check must not invent application-specific theme selectors.
6. Permanent configuration generation is explicit through `--write-config`; the unflagged command writes only the normal ignored `.statecraft/` evidence.
7. The generated config records only discovered public routes with one `public` state and a shared generated scenario. Developers extend it later for meaningful product states.
8. Existing schema-v1 result/report and artifact-path contracts can represent the quick-check cells without a report-schema change.

## Approaches Considered

- **Single supplied page:** fastest and safest, rejected because one page is unlikely to create the intended discovery moment.
- **Bounded public-site check:** strong zero-config report, but it throws away discovered route work instead of converting trial into adoption.
- **Bounded check plus generated permanent setup:** selected because it combines immediate evidence with a clean bridge into the full Statecraft workflow.

## Recommended Approach

### Command contract

```text
statecraft check <url> [--max-pages <1-20>] [--headed] [--write-config]
```

- `url` is required and must be one absolute HTTP(S) URL without credentials.
- `--max-pages` defaults to `5`, accepts integers from `1` through `20`, prevents duplicate specification, and caps attempted candidate navigations rather than only successful pages.
- `--headed` uses the existing visible-browser behavior.
- `--write-config` requests permanent starter files after a successful discovery/scan. Without it, Quick Check creates only `.statecraft/` output.
- Exit `0` when every quick-check cell passes, `1` when the report contains failures, and `2` for usage, discovery, safety, setup, or persistence errors.

The terminal summary prints the canonical origin, discovered/scanned/skipped page counts, each page result, issue totals, report path, and one exact adoption command when `--write-config` was not used.

### Discovery

Add a focused discovery module owned by the Playwright runner. It launches one Chromium process, gives every attempted page a fresh context, permits the supplied URL's initial HTTP(S) redirect chain, and uses the final response URL to establish the canonical origin. It then waits using Statecraft's readiness behavior and extracts at most the first 1,000 rendered anchor destinations in DOM order so an adversarial page cannot create an unbounded in-memory queue.

Discovery uses a queue:

1. Begin with the final canonical start page.
2. Normalize each rendered anchor by resolving it against the current page.
3. Keep HTTP(S), same-origin document URLs only.
4. Remove credentials, fragments, and query strings.
5. Preserve first-seen DOM order and enqueue unseen paths.
6. Continue sequentially until the queue is empty or `maxPages` candidate navigations, including skipped and failed candidates, have been attempted.

The initial navigation contract is explicit:

- DNS, TLS, timeout, unsupported-protocol, or other failures that produce no final HTTP(S) response cannot establish a canonical origin, so discovery stops with exit `2` and no completed report.
- A final initial response, including `4xx` or `5xx`, establishes the canonical origin and keeps the start path as a reportable route; its matrix cells fail on the main-document status.
- The initial redirect chain may change origin, such as an apex domain redirecting to `www`; only its final origin becomes canonical.

For later queued routes, discovery validates the final response URL after navigation. A same-origin route that fails navigation or returns an error response remains accepted so the scan can report it and `--write-config` can preserve it. A route that finishes on another origin is counted as skipped, is not scanned, and is not written to generated configuration. Playwright does not expose a stable high-level interception point for each server-redirect hop, so the destination can receive the browser's ordinary redirected GET before Statecraft detects and discards it; Statecraft never extracts or follows links from that destination. Discovery order and matrix expansion are deterministic for the same observed rendered DOM, but Statecraft does not claim repeated scans of a changing external site will discover identical pages or content.

### Quick-check execution

Build a deterministic matrix from discovered routes:

- route ID: readable path slug plus a short stable hash to prevent collisions;
- route path: canonical local pathname;
- state: `public`;
- viewports: `mobile` and `desktop`;
- themes: `light` and `dark` browser color-scheme preferences.

Add a small programmatic scenario override to the runner so Quick Check can use a trusted in-memory scenario instead of writing and importing a temporary executable module. Existing configured scans continue loading scenario files exactly as they do now.

The built-in public-site scenario:

- applies the requested browser color-scheme preference before navigation;
- runs the existing navigation/readiness/capture lifecycle;
- fails on main-document navigation/HTTP errors and uncaught page errors;
- records sanitized console messages and every subordinate request failure as warnings without failing the cell;
- asserts that the document root does not overflow horizontally beyond a small documented pixel tolerance;
- captures screenshots and preserves diagnostics even when a cell fails.

The runner persists the result through the existing `.statecraft/` lock, artifact tree, schema-v1 JSON, and offline HTML path. No new network service or report store is introduced.

### Permanent setup generation

With `--write-config`, preflight the target paths before launching a browser, then publish after a successful discovery and completed persisted scan:

```text
statecraft.config.mts
statecraft/
  scenarios/
    public/
      default.mts
```

The config contains the canonical base URL, every accepted route in discovery order, one shared `public` scenario path, mobile/desktop viewports, light/dark themes, and diagnostic failure policies. The scenario imports a documented runner-owned public-site assertion helper rather than copying evolving assertion code into the user's repository.

Extract and reuse the exclusive, config-last publication primitive from `statecraft init`. If any generated target or alternate supported config already exists, fail before browser work and name every conflicting path. Never merge into, overwrite, or delete an existing user config.

After generation, the CLI prints:

```text
Saved the discovered public surface.
Next: add real product states, then run `npx statecraft scan`.
```

The generated files must compile and the untouched generated `statecraft scan` must reproduce the same route matrix through the normal config-driven path.

### Public API boundaries

- Keep crawling and Quick Check orchestration inside `statecraft-ui-runner-playwright`.
- Expose one narrow runner function for the CLI rather than exposing crawler internals.
- Expose one documented public-site scenario/helper only if the generated scenario needs it.
- Keep URL and option parsing in `statecraft-ui`.
- Reuse `statecraft-ui-core` matrix, result, coverage, and artifact contracts without expanding them unless implementation proves a schema gap.

### First implementation slice: runner discovery

The first implementation PR exposes a small runner-owned API:

```ts
interface DiscoverPublicRoutesOptions {
  readonly launchOptions?: LaunchOptions;
  readonly maxPages?: number;
  readonly navigationTimeoutMs?: number;
  readonly readinessTimeoutMs?: number;
}

interface DiscoveredPublicRoute {
  readonly path: string;
}

interface PublicRouteDiscovery {
  readonly attemptedPages: number;
  readonly baseURL: string;
  readonly routes: readonly DiscoveredPublicRoute[];
  readonly skippedPages: number;
  readonly truncatedAnchorPages: number;
}

declare function discoverPublicRoutes(
  url: string,
  options?: DiscoverPublicRoutesOptions,
): Promise<PublicRouteDiscovery>;
```

The discovery state machine is deliberately small:

```text
START
  | validate options and strip input query/fragment
INITIAL NAVIGATION -- no response or non-HTML --> THROW
  | final response
CANONICAL ORIGIN + START PATH
  |
QUEUE -- fresh context --> same-origin HTML --> record final path + enqueue links
      |                --> navigation/readiness failure --> record requested path
      |                --> cross-origin or non-HTML --> skip
      |
      +-- queue empty or max attempts reached --> RETURN
```

The runner reuses one Chromium process and creates a fresh browser context for every attempted candidate. It extracts rendered anchors only after the existing deterministic readiness sequence and inspects at most the first 1,000 anchors on each page. The queue is first-seen breadth-first, and the hard `maxPages` budget counts every navigation attempt, including skipped and failed candidates.

Input and option validation fail before Chromium launches. The initial page failing to return an HTML response raises a sanitized discovery error because no trustworthy canonical surface exists. A later navigation or readiness failure keeps the requested same-origin path as a leaf; a later non-HTML response or cross-origin redirect consumes an attempt and is skipped. Browser creation, context creation, or cleanup failures abort the discovery run.

This slice does not expand a matrix, capture screenshots, run assertions, persist reports, implement CLI parsing, or generate configuration. Those remain in the explicitly ordered follow-up slices.

### Security and failure behavior

- Quick Check is authorized testing initiated by the local user. Documentation must tell users to check only sites they own or have permission to test.
- The tool performs sequential page navigation only. It does not intentionally click discovered links, submit forms, issue scripted mutations, retain cookies for export, or persist request/response bodies or headers. The loaded site's own JavaScript and ordinary requests still execute, so a page load is not guaranteed to be side-effect free.
- Existing diagnostic redaction remains mandatory for URLs, query values, credentials, tokens, cookies, and free-form errors.
- Browser and persistence cleanup runs for every success and failure path.
- A failed scan may still write a complete diagnostic report and exit `1`; a setup or safety failure exits `2` without claiming a completed report.

## Open Questions

- Whether a later release should honor a site's `robots.txt` in addition to the explicit ownership/permission requirement.
- Whether high-confidence accessibility checks belong in Quick Check after the zero-config workflow has real-user evidence.
- Whether generated configuration should eventually support authenticated-route promotion. Authentication is explicitly out of scope for this slice.

## Success Criteria

1. From a clean npm consumer with no Statecraft config, `npx statecraft check <fixture-url>` completes without source-file setup.
2. For the same observed rendered DOM, the default crawl attempts at most five candidate pages, returns unique same-origin paths in deterministic first-seen order, examines at most 1,000 anchors per attempted page, and never extracts or follows links from an external redirect destination; documentation discloses the one redirected GET and disclaims repeatability of live external content.
3. Five pages expand to exactly twenty cells across two viewports and two color-scheme preferences.
4. A deterministic fixture proves each supported high-confidence failure category, warning-only console/subordinate-request diagnostics, redirect boundary including the single external request, initial no-response error, hard navigation/anchor limits, and at least one healthy control for every assertion boundary.
5. The command writes four valid screenshots per accepted page, schema-v1 JSON, and self-contained offline HTML using existing collision-resistant artifact paths.
6. Diagnostics remain sanitized, bounded, and free of headers, cookies, bodies, URL credentials, fragments, and query values.
7. `--write-config` creates module-unambiguous `.mts` files without overwriting or traversing symbolic links; the generated config lists exactly the discovered routes.
8. An untouched `statecraft scan` using the generated files compiles, imports, executes, and reproduces the discovered public matrix.
9. CLI help, README quick start, package README, API/reference docs, security guidance, and an architecture decision record describe the honest boundary between `check` and `scan`.
10. Clean-checkout package smoke and a registry-only consumer exercise `check`, permanent setup generation, and the follow-up configured scan.

## What I Noticed About How You Think

- You started from the adoption barrier: “a lot of people might just want to use their existing website,” rather than asking for another advanced configuration feature.
- You defined the product moment by asking what result makes someone say, “I need this in my project.” That keeps the feature tied to evidence instead of command count.
- When offered the smaller bounded-check approach, you chose the version that converts discovered routes into a permanent setup. That prioritizes continued use over a disposable demo.
