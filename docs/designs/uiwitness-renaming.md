# Design: Rename Statecraft to UIWitness

Generated by `/office-hours` on 2026-08-24

Branch: `main`

Repo: `RujitRaval/statecraft`

Status: APPROVED

Mode: Builder

## Decision

Rename the public product from Statecraft to **UIWitness** before its first broad announcement.

This is an identity migration, not a redesign or feature release. Functional behavior, the report information architecture, the industrial-editorial visual direction in the [design system](../../DESIGN.md), and the current schema-v1 wire format remain frozen unless separately approved.

Primary brand line:

> Every exercised UI state leaves evidence.

Supporting copy:

> Find the UI states your product forgot.

Natural command language:

```bash
uiwitness check https://example.com
uiwitness scan
uiwitness open
```

## Problem Statement

Statecraft needs a distinct public identity before launch. An existing product already uses the Statecraft name for an overlapping frontend workflow built around product journeys, UI states, branches, and error paths. The current npm package `statecraft-ui` is valid and owned by this project, but npm ownership does not resolve the product-brand collision. The unrelated `statecraft` npm package and another CLI using a `statecraft` executable also make the current command identity harder to own.

UIWitness describes the product's strongest, supportable behavior: it exercises a defined UI surface and records evidence. It fits screenshots, assertions, diagnostics, coverage, offline reports, and future CI summaries without claiming automatic discovery of every hidden application state.

## Scope

In scope:

- Product, repository, package, executable, source-symbol, configuration, artifact, documentation, release, and launch-asset naming.
- Backward-compatibility and deprecation decisions for already-published Statecraft packages.
- Privacy-safe treatment of existing `.statecraft/` evidence.
- Registry bootstrap, provenance, trusted-publisher configuration, and rollback boundaries.
- Trademark and identifier clearance required before implementation.

Out of scope:

- New product capabilities, behavior changes, report redesign, or design-system changes.
- Schema-v2 work or opportunistic public API redesign.
- Automatic migration or deletion of a user's existing evidence.
- A permanent dual-brand strategy.

## Constraints and Premises

- The rename must complete before the public announcement so launch traffic builds one identity.
- The product remains local-first, deterministic, and free of required accounts, hosted services, telemetry, or LLMs.
- npm packages cannot be renamed in place; UIWitness requires new package identities.
- GitHub repository renames preserve redirects, but links, badges, release metadata, branch protection, environments, and trusted publishers still require explicit updates.
- The existing public Statecraft packages and executable need an intentional migration policy rather than silent abandonment.
- The clean identity must not erase historical truth or destroy potentially sensitive local reports.
- The clearance decision precedes implementation. Unclaimable identifiers are rechecked and claimed inside the protected release window.
- Because this is a continuation of the same product and repository, release history remains continuous. The first UIWitness packages use version `0.25.0`, with repository `VERSION` set to `0.25.0.0`; prior Statecraft tags and changelog entries remain historical records.

## Approaches Considered

### Brand-only alias — rejected

Market the product as UIWitness while retaining `statecraft-ui`, the `statecraft` executable, and `.statecraft/` artifacts. This is smaller but preserves the confusing identities users encounter during installation and support. It does not resolve the collision.

### Clean UIWitness identity — recommended

Use UIWitness consistently for the product, packages, executable, repository, generated files, artifacts, and documentation. Keep only explicit historical and migration references to Statecraft. Publish only after the pre-publication package-consumer gate passes; deprecate and announce only after the registry-only journey passes.

### Permanent compatibility layer — rejected

Maintain Statecraft aliases indefinitely alongside UIWitness. This doubles release, documentation, and support surfaces before meaningful adoption exists. A bounded bridge is permitted only if verified external use warrants it.

## Deliberate Statecraft Allowlist

After cutover, the old name is allowed only in:

- Historical Git tags, GitHub releases, changelog entries, and already-accepted architecture decisions.
- A migration/deprecation page that explicitly maps Statecraft to UIWitness.
- npm metadata and deprecation messages for the old packages.
- `.statecraft/` ignore rules and privacy-preservation tests.
- Legacy compatibility code, fixtures, or comments added only if the external-use threshold is met.

All other user-facing or generated occurrences fail the rename verification gate. Historical documents that are actively presented as current guidance must be updated even when their Git history is preserved.

## Blocking Decisions Before Implementation

### 1. Clearance and identifier ownership

The maintainer, Rujit Raval, owns the clearance record. Before implementation, check UIWitness for software, developer tools, UI testing, and adjacent services in intended launch geographies. Review trademark databases with appropriate professional advice where needed; this document is not legal advice. Record sources, jurisdictions, search terms, date, and retained evidence.

Secure or document the disposition of the preferred domain, npm names, GitHub identity, and launch-critical social handles. npm names cannot be safely reserved without publication, so the release window should minimize the interval between final registry recheck and first publish.

Preliminary checks on 2026-08-24 found no exact `uiwitness` npm package, exact GitHub repository, obvious web product, or registered `.com`; these findings are directional, not clearance.

The dated 2026-08-30 Gate 0 record narrows launch activity to the United States. The official USPTO wordmark search returned no live or dead exact `UIWitness` result. The maintainer approved `UIWitness`, confirmed that there are no known private or direct Statecraft consumers and no compatibility promises, and selected `deprecation-only`. No custom domain or launch-critical social handle is required; GitHub and npm are the canonical public destinations. The repository rename remains sequenced after the green implementation merge and immediately before publication, as defined below.

### 2. Schema namespace

Keep `schemaVersion: 1` and all current persisted fields unchanged. Rename the generated manifest filename to `uiwitness.json`, but ensure UIWitness report readers can open existing schema-v1 Statecraft payload fixtures. Rename public TypeScript symbols in the new packages. Do not add dual-name aliases to the new public API unless a verified external consumer requires them.

Any branded error value or internal literal must be classified during inventory as persisted wire data or implementation detail. Persisted values remain readable; implementation-only values are renamed. A schema change requires a separate approved decision.

### 3. External-use threshold

A compatibility release is required if any one of these is confirmed before cutover:

- A third-party repository imports or invokes a published Statecraft package.
- A third-party issue, discussion, or direct maintainer report demonstrates use.
- Another independently verifiable consumer artifact depends on the old package or executable.

Raw npm download counts do not qualify because automated release and smoke workflows can create them. If the threshold is not met, leave old package contents frozen and use registry deprecation messages only after UIWitness passes verification. Do not publish an old-package README-only release merely to change copy.

If the threshold is met, publish one final bounded bridge release whose legacy executable forwards with a deprecation warning and whose README points to UIWitness. Define its support end date before publishing it.

### 4. Privacy and local artifacts

Retain `.statecraft/` in `.gitignore` and add `.uiwitness/`. The new CLI must never automatically rename, copy, upload, or delete `.statecraft/`; those directories may contain screenshots and sensitive application data. Migration guidance may tell users how to retain or remove their own artifacts deliberately.

## Rollback-Safe Cutover Runbook

### Phase 0 — clear and claim

1. Complete the clearance record and approve the name.
2. Record that no domain or social identity is required and verify the intended GitHub identity remains available for the sequenced cutover.
3. Recheck all four npm names immediately before the protected release window.
4. Measure the external-use threshold and choose `deprecation-only` or `bounded bridge`.

No code rename begins until these blocking decisions are recorded.

### Phase 1 — reversible repository work

1. Start a focused rename branch from clean, current `main`.
2. Apply the migration matrix without behavior, schema, or visual redesign.
3. Preserve both evidence directories in ignore and privacy tests.
4. Update source, tests, docs, assets, package metadata, workflows, release configuration, and the [release guide](../open-source/RELEASING.md).
5. Run repository checks, package smoke tests, the full review workflow, and a dry-run release rehearsal while the repository retains its old remote name.
6. Merge only through a green pull request.

These changes are reversible through a follow-up pull request before npm publication.

### Phase 2 — final repository identity

1. Rename the GitHub repository to `RujitRaval/uiwitness` after the green merge and before publication.
2. Verify redirect, clone/fetch, default branch, branch protection, environments, secrets, workflow permissions, issue links, Pages or social metadata, and release automation.
3. Record and rehearse the exact repository, workflow filename, protected environment, and OIDC subject expected for every new package. The new-package settings cannot be configured until those package records exist.
4. If a legacy bridge is required, use maintainer-authenticated npm package settings to rebind the already-existing old packages to the renamed repository and dedicated bridge workflow before that workflow runs.
5. Rehearse the release subject and provenance expectations against the final repository identity.

The repository can be renamed back, but redirects and third-party links make repeated renames undesirable.

### Phase 3 — irreversible npm bootstrap

New npm packages cannot use trusted publishing until their package records exist. Therefore:

1. Create the `v0.25.0` GitHub Release from the renamed repository and approved commit.
2. Use a short-lived, granular npm automation token held only in the protected release environment to perform the first publication of the four new packages in dependency order, with `uiwitness` last.
3. Immediately configure OIDC trusted publishing for every new package against the final repository/workflow/environment.
4. Revoke and remove the bootstrap token immediately, then verify the next release path requires OIDC.
5. Confirm provenance, repository metadata, package access, executables, and dependency versions on npm.

Publication is irreversible in product terms. If verification fails, issue a forward fix; do not unpublish or reuse the version.

### Phase 4 — registry-only proof

From an untouched temporary consumer directory, using registry artifacts only:

1. Install `uiwitness`.
2. Run `uiwitness check <public-url>`.
3. Run `uiwitness check <public-url> --write-config` and verify overwrite safety.
4. Run the configured `uiwitness scan`.
5. Run `uiwitness open` and inspect the generated report.
6. Confirm package contents, terminal output, generated paths, JSON, and report UI contain no non-allowlisted Statecraft terminology.

Use the existing protected checks in the [release guide](../open-source/RELEASING.md) as the source of truth for the complete release gate.

### Phase 5 — old-package deprecation and announcement

1. If the external-use threshold was met, execute the conditional bridge runbook below only after Phase 4 proves the replacement.
2. Apply npm deprecation messages to old packages with the exact replacement command using a maintainer-authenticated npm website session or a one-off CLI session protected by 2FA. Trusted publishing does not authorize deprecation. Do not retain or reuse the bootstrap token.
3. Verify GitHub, npm, the social-preview asset, demo, README, and announcement all resolve to UIWitness.
4. Ask an unassisted external user to complete install → check → promotion → scan → open.
5. Announce only after that journey succeeds.

#### Conditional legacy bridge runbook

Run this only when the external-use threshold is met:

1. Freeze a bridge inventory from the observed usage. The default inventory is only `statecraft-ui`; include an old supporting package only when evidence shows direct imports that need it.
2. Version every bridge package at `0.25.0` and tag the approved commit `statecraft-bridge-v0.25.0`. Keep the UIWitness repository release contract at `v0.25.0`; the distinct tag makes the legacy publication auditable.
3. Use a dedicated protected bridge workflow and environment. Before running it, verify each included old package's npm trusted-publisher binding points to `RujitRaval/uiwitness`, that workflow, and that environment.
4. Publish bridge dependencies first and `statecraft-ui` last through OIDC. The primary legacy executable forwards to the verified `uiwitness` package and emits one precise deprecation warning; it must not duplicate implementation.
5. From a clean registry-only consumer, verify old-package installation, any evidenced legacy imports, executable forwarding, exit codes, and the exact migration message.
6. Set bridge support to end 90 days after the public UIWitness announcement. Record that date in the migration page and npm deprecation text.
7. If bridge publication fails, forward-fix the bridge with a new version. Do not delay or weaken the already-verified UIWitness package path.

## Success Criteria

- Clearance finds no blocking conflict, and launch-critical identifiers are either controlled or assigned an explicit protected-cutover step.
- One approved inventory accounts for every Statecraft occurrence as renamed, historical, privacy-preserving, or compatibility-only.
- A fresh user completes install → check → `check --write-config` → scan → open using only UIWitness names.
- All four UIWitness packages publish with provenance from the protected workflow; the bootstrap token is revoked and absent.
- Existing `.statecraft/` evidence is untouched and remains gitignored.
- Schema-v1 legacy fixtures remain readable without silently expanding the new public API.
- Old packages point users to UIWitness only after the replacement registry journey passes.
- Announcement links, the social-preview asset, npm page, GitHub repository, and demo assets use one identity.

## Risks and Responses

| Risk | Response |
| --- | --- |
| A late trademark or identifier conflict | Treat clearance and control as blocking; keep Statecraft unchanged until passed |
| npm squatting during cutover | Recheck immediately before a short protected publication window |
| Trusted-publisher mismatch after repository rename | Rename before publication and rehearse the final OIDC subject |
| First-package bootstrap weakens release security | Use one short-lived granular token, revoke immediately, then require OIDC |
| Hidden external consumers break | Use the evidence-based threshold and bounded bridge decision |
| Rename accidentally becomes a redesign | Freeze behavior, schema, information architecture, and design direction |
| Sensitive historical evidence is lost or committed | Retain both ignore rules; prohibit automatic migration or deletion |
| Bad immutable npm release | Forward-fix with a new version; never unpublish or overwrite |
