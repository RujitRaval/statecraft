# UIWitness Rename Implementation Plan

Generated by `/plan-eng-review` on 2026-08-24

Source design: [Rename Statecraft to UIWitness](../designs/uiwitness-renaming.md)

Status: ENGINEERING REVIEWED

## Objective

Rename the product, public packages, executable, generated project files, evidence paths, current documentation, release automation, and launch assets from Statecraft to UIWitness before public announcement.

This is one complete identity migration in one focused pull request. It does not change product behavior, the report information architecture, the visual system, or the schema-v1 field structure.

## Approved Engineering Decisions

1. Complete the repository-wide migration instead of leaving a mixed internal identity.
2. Keep `schemaVersion: 1`. New writers emit only `.uiwitness/`; report readers accept both `.uiwitness/` and legacy `.statecraft/` screenshot paths.
3. Never automatically rename, copy, upload, or delete an existing `.statecraft/` directory.
4. Add a dedicated, tested brand-contract checker and run it in local CI, pull-request CI, and release verification.
5. Reuse the existing protected first-publication workflow with a temporary granular npm token configured for All Packages read/write and bypass-2FA. Revoke the token and delete the environment secret immediately after trusted publishers are configured.
6. Require the full migration-specific regression matrix, including dual-root coexistence, privacy preservation, package smoke, and registry-only proof.
7. Preserve version continuity: repository `VERSION=0.25.0.0`, package versions `0.25.0`, and GitHub release `v0.25.0`.
8. Separate the schema-v1 compatibility contracts: report readers accept both evidence roots, while all writer and persistence types permit only `.uiwitness/`; legacy HTML links remain relative to the legacy input root.
9. Create a concrete legacy bridge only if verified external-use evidence exists. Otherwise, use deprecation-only messaging and create no legacy package source or workflow.
10. Split the first publication from registry verification. Verification is manually dispatched only after trusted-publisher configuration, bootstrap-token revocation, GitHub-secret deletion, and recorded evidence.
11. Prove the privacy boundary with filesystem-access instrumentation and permission-denial tests; byte-preservation checks remain a second safeguard.
12. Publish a dedicated `docs/open-source/MIGRATING_TO_UIWITNESS.md` migration guide.
13. Recover partial npm bootstraps with a fresh token per attempt, integrity-safe skipping of already-correct packages, dependency-first publication of only the missing remainder, and mandatory cleanup after every attempt.
14. Bind manual registry verification to an immutable release tag and resolved commit, including `VERSION`, ancestry, GitHub Release, and cleanup-evidence validation.
15. Classify intentional historical Statecraft text in the approved rename design and this engineering plan through narrow path-plus-pattern brand rules.
16. End any conditional bridge exactly 90 days after the public announcement, matching the approved design.
17. Preserve automatic registry-only verification after every normal OIDC release; disable that automatic edge only for the token-based bootstrap release, which uses the cleanup-gated manual workflow.

## Architecture

### Runtime and evidence flow

```text
uiwitness CLI
  |
  +--> init/check --write-config
  |      |
  |      +--> uiwitness.config.mts
  |      +--> uiwitness/scenarios/**
  |
  +--> check/scan
         |
         +--> uiwitness-core
         |      +--> config + schema-v1 read/write contracts
         |      +--> .uiwitness/artifacts path generation
         |
         +--> uiwitness-runner-playwright
         |      +--> existing capture lifecycle
         |      +--> existing atomic persistence transaction
         |
         +--> uiwitness-report
                +--> parses schema v1 through a dual-root read contract
                +--> accepts .uiwitness/ screenshot paths
                +--> accepts legacy .statecraft/ screenshot paths
                +--> resolves links relative to the input evidence root
                +--> emits UIWitness-branded offline HTML
```

### Evidence compatibility boundary

```text
NEW WRITE
  ExecutionResult.screenshotPath = .uiwitness/artifacts/...
  report output                = .uiwitness/report/uiwitness.json

READ CONTRACT (parser + transformer)
  .uiwitness/artifacts/...  --> accepted --> href relative to .uiwitness report
  .statecraft/artifacts/... --> accepted --> href relative to .statecraft report
  any other root            --> rejected before transformation

WRITE CONTRACT (generator + persistence)
  .uiwitness/artifacts/...  --> accepted
  .statecraft/artifacts/... --> type/runtime rejection

LOCAL PRIVACY
  .statecraft/**  --> never read, moved, copied, or deleted by a new run
  .uiwitness/**   --> owned by the existing safe persistence transaction
```

The read compatibility rule begins in `packages/core/src/results.ts`, before `parseReport` can reject the legacy value, and continues through `packages/report/src/transform.ts`. A dedicated read-path type is a two-root union; writer and persistence APIs use a distinct new-root-only type. Core schema fields remain unchanged. The transformer derives an HTML-relative screenshot href from the accepted input root, so a legacy report never points at `.uiwitness/artifacts/**` by mistake. The new CLI's `open` command targets only `.uiwitness/report/index.html`; legacy compatibility is programmatic report reading, not silent filesystem migration.

### Package graph

```text
uiwitness-core
      |
      +--> uiwitness-report
      |          |
      +----------+--> uiwitness-runner-playwright
                              |
                              +--> uiwitness
```

Keep the existing workspace directories `packages/core`, `packages/report`, `packages/runner-playwright`, and `packages/cli`. Directory names already describe responsibilities and do not carry the colliding brand.

### Release state machine

```text
[clearance + identifiers controlled]
                  |
                  v
[rename PR green and merged]
                  |
                  v
[GitHub repo renamed to RujitRaval/uiwitness]
                  |
                  v
[bootstrap workflow + temporary bootstrap token]
                  |
                  v
[four new packages published, uiwitness last]
                  |
                  v
[mandatory cleanup gate, including failed publish]
  owner: Rujit; deadline: within 30 minutes
  configure four trusted publishers
  revoke bootstrap token
  delete GitHub NPM_TOKEN secret
  record checklist evidence
                  |
                  v
[manual registry-verification workflow]
  input: immutable release tag
  resolve + check out exact tag commit
  bind VERSION, ancestry, Release, cleanup evidence
  registry-only check -> promote -> scan -> open
                  |
                  v
[conditional bridge if evidence requires it]
                  |
                  v
[old packages deprecated with exact replacement]
                  |
                  v
[external-user proof -> public announcement]
```

No npm package is unpublished. A bad immutable release is corrected with a new version.

For the bootstrap release, publication and registry verification are separate workflows or separately dispatched jobs with no automatic dependency edge between them. The bootstrap verification workflow requires an immutable release-tag input and the cleanup evidence as a protected-environment approval input. It resolves and checks out the tag's commit rather than the dispatch branch, then binds `VERSION`, tag ancestry, GitHub Release identity, and cleanup evidence to that exact tag/SHA. GitHub Actions cannot itself prove that an npm token was revoked or that an external secret was deleted, so the human checklist is an explicit release artifact.

After bootstrap, normal releases use the trusted publisher and OIDC without `NPM_TOKEN` and retain the existing automatic publication-to-registry-verification dependency. A tested explicit bootstrap-mode condition disables that automatic edge only when the temporary token path is active; it must not weaken or remove the final registry-only job for ordinary releases.

If publication is partial, compare every existing package/version against the local tarball integrity. Skip only exact matches using the existing integrity-safe behavior in `scripts/publish-release-packages.mjs`; an integrity mismatch stops the release and requires a forward version. For packages that do not yet exist, Rujit creates a fresh minimum-expiration bootstrap token, publishes only the missing dependency-first remainder, and repeats publisher configuration, revocation, secret deletion, and evidence capture within 30 minutes of that attempt's success or failure. Never reuse a bootstrap token between attempts.
